# Application review agent

A small GPT-powered reviewer for the three fictional Customer Support Specialist applications. The model calls real Python functions through a local MCP server. Python validates the evidence, recomputes the score, enforces the route, and logs the result. **The rejection function can only record `waiting for human approval`.**

## Run

Requires Python 3.11+ and a current [Codex CLI](https://developers.openai.com/codex/cli/) with `--ignore-user-config` support and a signed-in account that can use the selected GPT model.

```sh
python -m venv .venv
# macOS/Linux
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
codex login
python run.py --export artifacts/my-run.json
```

The default model is `gpt-6.1-sol`; change it with `--model` if your account uses a different model name. `CODEX_BIN` can point to an explicit Codex executable when your desktop app and PATH CLI versions differ. Credentials stay with Codex: no API keys, tokens or personal configuration are copied into the repository.

Run offline safety tests with `python -m unittest -v`. Tests use fixed inputs and are **not** represented as LLM results. The script fails with a nonzero exit code on model/auth/tool errors; it never substitutes a simulated decision. Export files must be new paths, preserving earlier evidence. Raw local diagnostics are kept under ignored `runs/`.

## What the model does

Each application gets its own fresh session. GPT reads the untrusted text, extracts explicit facts with exact supporting quotes, gives a one-line explanation, and calls one of:

- `advance_to_interview`
- `reject`
- `request_more_info`

The MCP server exposes those three tools. Built-in shell, file-editing, browser search, apps, other MCP servers, hooks, and agent delegation are disabled for the review process. Approval is granted only to this local review server. These functions write local decisions; they do not contact candidates or an employer's systems.

`run.py` verifies an actual completed MCP call/result and exactly one recorded decision per application. The exported JSON includes model-selected arguments, tool results, UTC audit events, score breakdowns, and source hashes.

## Explicit demo policy

Because no full job description was supplied, the demo assumes an experienced support position requiring at least one year of support experience, fluent English, and full-time availability. These are design assumptions, not Besa's stated hiring requirements.

| Evidence | Points |
|---|---:|
| At least 2 years of support / at least 1 year | 40 / 25 |
| At least 40 tickets a day / positive lower volume | 15 / 5 |
| Named supported ticketing tool | 15 |
| Explicit fluent English | 20 |
| Explicit full-time availability | 10 |

Missing evidence contributes zero points but is **not** treated as an explicit failed requirement. The score measures evidence for this rubric, not a person's worth or general ability. Names and protected characteristics are not scored.

1. Suspected injected instructions -> request more information / human review, without deducting points.
2. Explicit failure of an assumed requirement -> propose rejection, pending human approval.
3. Score at least 70 and all three requirements confirmed -> advance.
4. Otherwise -> request missing information.

This intentionally routes John's explicit lack of experience to a proposed rejection. For an entry-level role, remove that assumed minimum; unknown fields should still trigger clarification.

## Safety boundaries

- Trusted instructions are separate from the application record. Application text is never a system instruction.
- Tool inputs use a strict schema. A model cannot supply an approval flag, status override, arbitrary score, candidate ID, output path, or tool name outside the allowlist.
- Known facts need exact evidence quotes. Python checks simple numeric, tool, language and availability patterns and calculates points itself.
- A conservative instruction detector supplements the model's injection flag. Sample C's attempted override cannot assign a score of 100.
- The rejection function hard-codes its pending status. There is no approval or final rejection tool available to the model.
- Tool attempts, validation errors, decisions and results are written to JSONL. Logging must succeed before an action is acknowledged. Duplicate decisions within a review session are blocked.

These are layered safeguards, **not a claim that prompt injection is solved**. Evidence checks deliberately support a small set of English patterns and tool names; sophisticated semantic deception, omitted negation, unusual phrasing and false positives need a larger evaluation set. The local audit is inspectable, not tamper-proof. No real hiring data is used.

## Next steps

Before production: agree the role rubric with a human hiring manager; add an authenticated human review queue and durable idempotency; test multilingual and adversarial paraphrases; evaluate error rates and fairness; add retention/access controls and tamper-evident audit storage. Keep the human gate outside model control.
